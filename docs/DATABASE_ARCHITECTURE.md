# NOEMA — მონაცემთა ფენის არქიტექტურა

**სტატუსი:** ტექნიკური წინადადება, ჯერ არ არის დანერგილი  
**ვერსია:** 1.0  
**თარიღი:** 2026-11-24

## 1. ამჟამინდელი მდგომარეობა

საჯარო ვებსაიტი იყენებს Git-ში შენახულ `data/research.json` კატალოგს. კატალოგი ვერსიაკონტროლირებადია, მარტივი და build-ის დროს ვალიდირდება, მაგრამ ის **არ არის ტრანზაქციული სერვერული მონაცემთა ბაზა**. მას არ აქვს მომხმარებლის ავთენტიფიკაცია, DB-level კომენტარები, მონაცემთა ცოცხალი განახლება ან ადმინისტრაციული როლები.

ამჟამინდელი საჯარო შედეგები:
- `preliminary` — წინასწარი, მკაფიო გაფრთხილებით;
- `published` — დამოუკიდებელი/სარედაქციო შემოწმების შემდეგ;
- `draft` და `review` — საიტის საჯარო კატალოგში არ უნდა მოხვდეს.

## 2. მიზნობრივი არქიტექტურა

შემოთავაზებულია NOEMA-სთვის ცალკე Supabase/Postgres პროექტი, რომელიც სამ ნაწილად იყოფა:

1. **კვლევები** — ჩანაწერი, სტატუსი, ვერსია, შინაარსი, ავტორი, შექმნის/განახლების დრო.
2. **მტკიცებულებები** — წყაროები, ციტირებები, მონაცემთა ნაკრებები, SHA-256, ლიცენზია და წარმოშობის მონაცემები.
3. **საზოგადოებრივი ჩართულობა** — განხილვები, კომენტარები და რეცენზიის ჩანაწერები.

ავტომატიზაციის ტექნიკური ჟურნალი ინახება კერძო `noema_private` სქემაში და არ გამოისახება საჯარო Data API-ით.

### მონაცემთა ნაკადის სურათი

```text
კვლევითი ავტომატიზაცია
        |
        v
 სამუშაო ვერსია (draft)
        |
        v
 წყაროები + მონაცემები + გამეორებადი ტესტები
        |
        v
 სარედაქციო განხილვა (review)
        |
        +---- უარყოფა / შესწორება ----> draft
        |
        v
 წინასწარი შედეგი (preliminary)
        |
        v
 საჯარო ვებსაიტი + განხილვები
        |
        v
 დამოუკიდებელი რეცენზია და ახალი ვერსიის შემოწმება
        |
        v
 საბოლოო გამოქვეყნება (published)
```

## 3. წვდომის მოდელი

| როლი | კვლევების ნახვა | კვლევის შექმნა | განხილვა | რეცენზია | გამოქვეყნება |
|---|---|---|---|---|---|
| სტუმარი (anon) | მხოლოდ preliminary/published/retracted | არა | საჯარო კომენტარების ნახვა | არა | არა |
| რეგისტრირებული მომხმარებელი | საჯარო + საკუთარი draft | draft | საჯარო კვლევაზე კომენტარი | არა | არა |
| რეცენზენტი | საჯარო + მისთვის ხელმისაწვდომი review | draft | კომენტარი | სხვა ავტორის review | არა |
| რედაქტორი | ყველა | დიახ | მოდერაცია | დიახ | preliminary |
| ადმინისტრატორი | ყველა | დიახ | მოდერაცია | დიახ | published, მხოლოდ დამტკიცების წესის დაცვით |

**უფლებამოსილების წყარო:** როლები უნდა ინახებოდეს სანდო `app_metadata` claim-ში (მაგ. `noema_role`), რომელსაც მართავს მხოლოდ სერვერის/ადმინისტრატორის მხარე. მომხმარებლის მიერ შეცვლადი `user_metadata` ავტორიზაციისთვის არ გამოიყენება. JWT-ის ცვლილება მომხმარებელს განახლებული ტოკენის მიღებამდე შეიძლება არ დაენახოს.

## 4. უსაფრთხოება

- ყველა `public` ცხრილზე ჩაირთოს RLS.
- `anon`-ს მიეცეს მხოლოდ საჭირო `SELECT` წვდომა; წვდომა შეზღუდული იყოს სტატუსის მიხედვით.
- `authenticated`-ს მიეცეს კონკრეტული ოპერაციები; ცხრილის GRANT და RLS პოლიტიკა ორივე საჭიროა.
- კერძო დრაფტები ხელმისაწვდომი იყოს ავტორისთვის და უფლებამოსილი რედაქტორისთვის.
- რეცენზიის ჩანაწერი იყოს append-only; რეცენზენტმა არ უნდა შეაფასოს საკუთარი ნაშრომი.
- `published` სტატუსზე გადასვლა მოითხოვდეს იმავე ვერსიის მინიმუმ ერთ დამტკიცებულ რეცენზიას, რომლის ავტორიც არ არის კვლევის ავტორი. ეს არის ტექნიკური მინიმალური ბარიერი და არა ინტერესთა კონფლიქტის სრულყოფილი შემოწმება.
- `service_role` და secret key არასოდეს მოხვდეს ბრაუზერში, HTML-ში ან საჯარო GitHub-ში.
- კომენტარების სიხშირე/სპამი კონტროლდებოდეს სერვერული Edge Function-ით ან rate limit-ით; მხოლოდ RLS სპამისგან დაცვა არ არის.
- ახალი Supabase პროექტი უნდა იყოს NOEMA-სთვის ცალკე. სხვა პროექტების ბაზა არ გადაიბას.

## 5. კვლევის ვერსიები და გამოქვეყნების გარანტია

თითოეული კვლევა ინახავს მთელ რიცხვით `version`-ს. წყაროს, ტექსტის, მეთოდის ან შედეგის არსებითი ცვლილება ვერსიას ზრდის. რეცენზია უკავშირდება კონკრეტულ `reviewed_version`-ს; ძველი ვერსიის დამტკიცება ახალ ვერსიას ავტომატურად არ ამტკიცებს.

SQL-ის წინადადებაში ჩართულია trigger, რომელიც `published` სტატუსზე გადასვლას ბლოკავს, თუ იმავე ვერსიაზე არ არსებობს სხვა მომხმარებლის მიერ გაცემული `approve` რეცენზია. დამატებით, სერვერულმა გამოქვეყნების პროცესმა უნდა გადაამოწმოს CI, მონაცემთა provenance, ლიცენზია და რედაქციული საკონტროლო სია.

## 6. საიტთან ინტეგრაცია

საწყის მიგრაციაში მიმდინარე Git JSON კატალოგი რჩება fallback-ად. შემდეგ ეტაპზე:

1. საიტი კითხულობს საჯარო view/API-ს, რომელიც აბრუნებს მხოლოდ `preliminary`, `published` და `retracted` ჩანაწერებს.
2. კვლევის გვერდი აჩვენებს სტატუსს, ვერსიას, წყაროებს, მონაცემთა წარმოშობას, მეთოდს, შეზღუდვებს და ცვლილებების ისტორიას.
3. კომენტარები იტვირთება ცალკე endpoint-იდან; ახალი კომენტარის დასამატებლად საჭიროა Supabase Auth.
4. თუ ბაზა მიუწვდომელია, საიტი აჩვენებს ბოლო წარმატებით გენერირებულ სტატიკურ კატალოგს და მიუთითებს, რომ მონაცემები შესაძლოა განახლებული არ იყოს.
5. GitHub Issues-ის არსებული განხილვის ბმულები შენარჩუნდება გარდამავალ ეტაპზე.

## 7. სარეზერვო ასლები და აღდგენა

- ავტომატური ყოველდღიური backup უნდა ჩაირთოს პროექტის გეგმასა და შესაძლებლობებზე დაყრდნობით.
- გამოქვეყნების ყოველი ციკლის წინ ექსპორტირდეს კვლევის მეტამონაცემები, წყაროები, review-ები და კომენტარები.
- ნედლი მონაცემები არ ჩაიწეროს DB-ში, თუ მონაცემის ლიცენზია ან ზომა ამის საშუალებას არ იძლევა; ასეთ შემთხვევაში შეინახოს წყარო, hash და ლიცენზია.
- კვარტალში ერთხელ შესრულდეს აღდგენის საცდელი პროცედურა ცალკე staging გარემოში.
- backup-ის არსებობა აღდგენადობის მტკიცებულება არ არის; აღდგენა უნდა გაიტესტოს.

## 8. დანერგვის წინაპირობები

ეს წინადადება **არ არის გაშვებული SQL მიგრაცია** და არც Supabase პროექტია შექმნილი.

დანერგვამდე საჭიროა:
- NOEMA-სთვის ცალკე Supabase პროექტის შექმნა და ორგანიზაციის/რეგიონის/ფასის არჩევა;
- ხარჯის პირობების დადასტურება, თუ პროექტს ფასი აქვს;
- სანდო `app_metadata.noema_role` ადმინისტრირების პროცედურა;
- staging პროექტზე RLS ტესტები anon/authenticated/editor/reviewer/admin სცენარებით;
- SQL lint/advisors შემოწმება;
- backup/restore საცდელი პროცესი;
- საიტის API და static fallback ტესტები.
