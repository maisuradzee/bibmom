შეუძლია თუ არა CPython 3.14.4 free-threaded build-ს x86-64 გარემოში Neumaier compensated reduction-ის wall-time დაჩქარება ისე, რომ exact-reference სიზუსტე შენარჩუნდეს, და რამდენად დამოკიდებულია შედეგი hosted runner backend-ზე?

## მეთოდი

სამი GitHub Actions workflow run-ის ექვსი report ჩამოტვირთულია: [46034414138](https://github.com/maisuradzee/bibmom/actions/runs/46034414138), [46034729099](https://github.com/maisuradzee/bibmom/actions/runs/46034729099) და [46035393777](https://github.com/maisuradzee/bibmom/actions/runs/46035393777). თითო report მოიცავს 48 configuration-ს, თითოეულზე სამი measured repetition-ით (ერთი warm-up): ორი deterministic input layout, 1/2/4/8 worker, contiguous/round-robin partition და naive scalar / scalar Neumaier / Neumaier-state მეთოდები. სულ: 288 configuration და 864 measured run.

Speedup-ის baseline მეთოდთან შესაბამისია: naive threaded-ს ადარებენ serial naive-ს; ორივე Neumaier threaded მეთოდს — serial Neumaier-ს. Reference არის input binary64 მნიშვნელობების exact rational sum, ერთხელ binary64-ზე დამრგვალებული. Wall time იზომება perf_counter_ns-ით, process CPU — process_time_ns-ით, მეხსიერება — tracemalloc peak delta-ით.

Across all six reports: Neumaier state **288/288**, scalar Neumaier **252/288**, naive scalar **0/288** correctly rounded configurations. Process CPU/wall >1.05 occurred in **324/432** free-threaded samples and **0/432** GIL-enabled samples.

The two Azure free-threaded reports show Neumaier-state median speedup above 1.0 at 2/4/8 workers. The matched Azure pair (run 46034414138) has GIL 0.7809× and free-threaded 1.3172×. The matched AWS pair (run 46035393777) has GIL 0.7646× and free-threaded 0.7034×: free-threaded CPU/wall ratios exceed 1.05 for multi-worker cases, but wall-time speedup is absent. This is a material backend-dependent result.

## INFERENCE

The results do not support a general claim that free-threading speeds up this reduction. Azure hosted free-threaded runs show >1.0 median speedup for 2/4/8 workers, while the matched AWS free-threaded run remains below 1.0 at every worker count despite evidence of parallel CPU activity. Runner backend, virtualized CPU model, scheduling, cache, frequency/power policy or other host characteristics may dominate. These causes are not isolated by this experiment.

## HYPOTHESIS

The observed Azure/AWS divergence may be driven by host CPU generation, virtualization, memory/cache topology or runtime build differences. A controlled same-host design is required to distinguish them.

## UNTESTED IDEA

Run at least 20 measured repetitions per configuration on fixed, independently controlled x86-64 and ARM64 machines; pin CPU model, microcode, affinity, OS image and power policy; add RSS/native allocator, DRAM bandwidth, per-thread CPU clocks and confidence intervals. Compare multiple chunk sizes and tree-reduction strategies.

## LIMITATIONS

- GitHub-hosted x86-64 VMs are not physical-device or external-laboratory replication.
- Three repetitions per configuration are insufficient for robust uncertainty estimates.
- The deterministic cancellation inputs are synthetic, not representative production workloads.
- tracemalloc does not measure full process RSS, native allocator overhead or DRAM bandwidth.
- Run 46034729099 has a mixed-backend pair (AWS GIL, Azure free-threaded) and is not a matched runtime comparison.
- The matched Azure and AWS pairs use separate hosted VMs, not the same physical host.
- CPU/wall >1.05 indicates aggregate CPU consumption above wall time; it is not itself a speedup or throughput metric.
- The Quality CI associated with run 46035393777 initially failed on a misworded new test assertion; the benchmark workflow itself succeeded. The assertion was corrected and the current exact-head Quality CI is being re-run.
